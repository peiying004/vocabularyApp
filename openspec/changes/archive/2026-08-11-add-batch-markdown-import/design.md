## Context

`add-content-editing` 已經在 Model 層建立了 `CardEditor` 與 `GrammarItemEditor`，承載匯入之後、單一批次內的內容變更：欄位驗證、容量檢查、`importOrder` 指派、刪除時的空批次移除與批次重新編號。批次容量統一為 40，由 `CardImporter.chunkSize` 與 `GrammarItemImporter.chunkSize` 單一定義，兩個 Editor 的 `capacity` 取自它。

匯入路徑目前只有一條：`ImportView` / `GrammarImportView` 把整份文字交給解析器，再由 `CardImporter.appendCards` / `GrammarItemImporter.appendItems` 依 `chunkSize` 切批，接在 deck 末端。它不接受「寫進某個既有批次」這個目標。

預習頁的「＋」目前直接開啟編輯畫面的新增模式，一次只能加一筆；批次已滿時按下會顯示提示視窗並拒絕。

現有限制：批次還有空位時，想一次補多筆內容只能逐筆手動輸入，或改用 deck 層級匯入而被迫另開新批次。

約束：

- 批次容量 40 是所有寫入批次的操作都必須遵守的硬上限（`vocabulary-import` 的 Batch Capacity Invariant）。
- `Batch.cards` 與 `GrammarBatch.items` 是 `private(set)`，只能透過設定 `card.batch = batch` 加入成員。
- 解析器的回傳形狀是 `(cards/items, errors)`，錯誤含行號與原始行內容。
- `ImportView` 已建立「無效行（已跳過）」的回報慣例，列出行號與原始內容。
- 本專案的驗收不含模擬器互動操作。
- 本 change 修訂 `content-editing` 的需求，而該 capability 的主 spec 尚未存在——它會在 `add-content-editing` 歸檔時建立。因此實作順序上必須先歸檔 `add-content-editing`。

## Goals / Non-Goals

**Goals:**

- 讓使用者能一次把多筆內容補進**正在看的那一個批次**，不必逐筆輸入，也不必被迫另開批次。
- 讓「貼進來的比剩下的空位多」這件事由使用者決定怎麼處理，而不是系統替他決定。
- 讓剩餘容量計算、部分填入、溢出切批這三件事都留在可單元測試的 Model 層。
- 讓溢出時建立新批次的行為與匯入完全一致，不出現第二套切批規則。

**Non-Goals:**

- 不改變 deck 層級匯入頁的既有行為。
- 不支援從檔案選取匯入到單一批次。
- 不改變解析器的欄位規則或容錯行為。
- 不改變批次容量 40，也不重新切分既有批次。
- 不支援指定溢出內容要進入哪一個既有批次。
- 不提供匯入的復原（undo）。
- 不建立 XCUITest target，驗收不含模擬器互動操作。

## Decisions

### 超量時由使用者選擇開新批次或放棄，而非系統自行決定

貼上的有效筆數超過該批次剩餘格數時，顯示確認視窗，兩個選項：「開新批次」把目前批次填滿、其餘切成新批次接在 deck 末端；「放棄此次新增」一筆都不寫。

替代方案一，靜默只收前 N 筆、其餘丟棄：否決。資料無聲消失是最糟的結果。

替代方案二，只收前 N 筆並在回報區列出未匯入的內容：這是可接受的，但仍要使用者自己想辦法處理剩下的，而處理方式就是「再去別的地方匯入一次」——不如直接問他要不要現在就開新批次。

替代方案三，自動溢出到新批次不詢問：這正是 `add-content-editing` 兩度否決的做法，理由是「在批次 1 操作卻看到內容出現在批次 3」是無法預期的副作用。加上一道確認視窗之後這個理由消失了：使用者被明確告知、自己選的結果不是副作用。這個決策與先前的否決並不矛盾，差別就在知情同意。

「放棄」是全有全無，不會留下寫了一半的狀態要使用者收拾。

### 溢出切批直接重用 Importer，不另寫切批邏輯

填滿目前批次之後的剩餘內容，交給既有的 `CardImporter.appendCards` / `GrammarItemImporter.appendItems` 處理。它們已經負責依 `chunkSize` 切批、接續既有最大批次編號往下編。

這確保「溢出建立的新批次」與「匯入建立的新批次」在大小、編號、`importOrder` 上完全一致，不會出現第二套規則。剩 82 筆就切成 40、40、2 三批，與直接匯入 82 筆的結果相同。

替代方案：在 Editor 裡自己實作切批。否決，因為那會複製 Importer 的邏輯，兩處規則日後可能分歧。

### 批量寫入的容量計算放在 Editor，與單筆新增同層

`CardEditor` 與 `GrammarItemEditor` 各增加剩餘容量查詢與批量寫入兩項行為。批量寫入負責：填滿目前批次到 `capacity` 為止、視旗標決定是否把其餘交給 Importer、回傳寫入統計。

這與既有的單筆 `appendCard` / `appendItem` 在同一層，共用同一個 `capacity` 來源與同一套欄位驗證，因此不可能出現「單筆守上限、批量不守」這種分歧。也讓部分填入與溢出切批能被單元測試覆蓋，不必靠操作畫面驗證。

替代方案：把計算寫在貼上畫面裡。否決，理由與 `add-content-editing` 相同——View 層沒有測試覆蓋，而容量與切批正是最需要迴歸保護的部分。

### 「＋」改為選單入口，滿載時續往新批次而非死路

「＋」原本直接開啟編輯畫面的新增模式，現在改為跳出選單（`手動輸入一筆` / `貼上 Markdown`）。

批次已滿時按「＋」顯示提示視窗說明批次已滿，並提供「開新批次」與「取消」。選「開新批次」後開啟同一個選單，差別只在寫入目標由「目前批次」變成「deck 末端新建立的批次」；選「取消」則不做任何事。

這與超量貼上的處理是同一個原則：**系統不替使用者決定，但也不把他留在死路上**。既然超量時可以選擇開新批次，滿載時沒有理由只能被擋下來——滿載其實就是「剩餘容量為 0 的超量」，是同一件事的邊界情況。

替代方案，維持完全阻擋、指引使用者改用 deck 層級匯入頁：否決。使用者要多退兩層導覽、選對 deck、再貼一次，而系統其實完全知道他想加到哪個 deck。

「＋」本身仍然不加 `.disabled`，維持 `add-content-editing` 的決策：停用的按鈕按不下去，使用者就無從得知原因。

### 新批次在儲存時才建立，不存在空批次狀態

`content-deletion` 明訂「空批次不得留存」，而 `add-content-editing` 當初否決「手動建立空批次」正是因為這條規則會與之衝突。

本 change 不建立空批次：新批次一律由 `CardImporter.appendCards` / `GrammarItemImporter.appendItems` 在寫入內容的同時建立，內容與批次一起產生。手動輸入一筆的情況也走同一條路——把那一筆當成「只有一筆的匯入」，產生一個含 1 筆的新批次。

因此不需要「先建批次、再填內容」的中間狀態，也就沒有空批次可以留存，與 `content-deletion` 沒有衝突。這也讓「滿載時手動新增一筆」與「滿載時貼上多筆」共用同一套建批與編號規則。

替代方案，先建立空批次再讓使用者填：否決。除了與空批次規則衝突，使用者中途取消還會留下一個要清理的空批次。

### 無效行與超量是兩件事，分開呈現

解析出的無效行（欄位數不對、必填欄位空白）沿用既有規則：跳過、不計入有效筆數、在回報區列出行號與原始內容。

超量判斷只看**有效筆數**與剩餘格數。兩者在畫面上分成兩區：無效行是「這幾行我看不懂」，超量是「這批放不下」，原因不同、使用者的後續動作也不同，合併呈現會讓人搞不清楚到底發生什麼事。

## Implementation Contract

**Behavior**

單字側（文法側對稱，差別只在欄位與型別）：

- 在未滿的批次預習頁按「＋」，出現選單，含「手動輸入一筆」與「貼上 Markdown」兩項。
- 選「手動輸入一筆」，行為與現況完全相同：以 sheet 開啟空白的 `CardEditView` 新增模式。
- 選「貼上 Markdown」，以 sheet 開啟批次貼上畫面，畫面顯示目前批次還能放幾筆。
- 貼上文字並確認後解析：無效行不計入有效筆數，於回報區列出行號與原始內容。
- 有效筆數小於或等於剩餘格數：全部寫入目前批次，`importOrder` 由該批次現有最大值加 1 起連續遞增，每筆 `wrongCount` 為 0；回報新增筆數。
- 有效筆數大於剩餘格數：顯示確認視窗，說明還能放幾筆、有幾筆放不下，提供「開新批次」與「放棄此次新增」。
  - 選「開新批次」：先寫入足以填滿目前批次的前幾筆，其餘依批次容量切批、接在 deck 末端建立新批次；回報總新增筆數與新建批次數。
  - 選「放棄此次新增」：不寫入任何一筆，目前批次與 deck 的批次數皆不變。
- 已滿的批次按「＋」：顯示提示視窗說明批次已滿，提供「開新批次」與「取消」。
  - 選「取消」：不開啟任何畫面，不寫入任何內容，deck 批次數不變。
  - 選「開新批次」：開啟同一個選單。選「手動輸入一筆」並儲存後，deck 末端新增一個含該筆內容的批次；選「貼上 Markdown」並確認後，有效內容依批次容量切批、接在 deck 末端。兩者都不會動到原本已滿的批次。

**Interface / data shape**

`CardEditor` 新增兩項（`GrammarItemEditor` 對稱）：

- 剩餘容量：輸入一個 `Batch`，回傳 `capacity` 減去該批次現有卡片數，最小為 0。
- 寫入新批次：輸入解析後的內容陣列、目標 `Deck` 與 `ModelContext`，把內容交給 `CardImporter.appendCards` 依批次容量切批、接在 deck 末端；回傳總寫入筆數與新建立的批次數。空輸入不建立任何批次。
- 批量寫入：輸入解析後的內容陣列、目標 `Batch`、一個是否允許溢出的旗標與 `ModelContext`。行為為：
  - 先過濾掉未通過欄位驗證的項目（正常情況下解析器已保證通過，此處為防禦）。
  - 取前「剩餘容量」筆寫入目標批次，`importOrder` 接續該批次現有最大值。
  - 若仍有剩餘且旗標為允許溢出，把剩餘交給對應的 Importer 寫入該批次所屬的 deck。
  - 若仍有剩餘但旗標為不允許溢出，不寫入任何一筆並回傳 nil。
  - 回傳寫入結果：寫入目標批次的筆數、新建立的批次數、總寫入筆數。

`BatchImportView` 與 `GrammarBatchImportView`（SwiftUI View，以 sheet 呈現）：接受目標批次，提供多行文字輸入、剩餘容量提示、確認匯入動作、無效行回報區與匯入結果回報區，並在超量時以確認視窗取得使用者選擇。

`PreviewView` 與 `GrammarPreviewView`：「＋」的 action 先檢查 `canAppend`。true 時開啟選單，兩個選項分別以目前批次為目標開啟編輯畫面新增模式與批次貼上畫面。false 時顯示「本批次已滿」提示視窗；使用者選「開新批次」後開啟同一個選單，但兩個選項改以所屬 deck 為目標。

`CardEditView` 與 `GrammarItemEditView` 的新增模式需支援兩種寫入目標：既有批次（沿用現況）與 deck 末端的新批次。後者在儲存時把單筆內容交給上述「寫入新批次」函式。

`BatchImportView` 與 `GrammarBatchImportView` 同樣需支援兩種目標：目標為既有批次時走剩餘容量與超量流程；目標為 deck 時所有有效內容一律進新批次，不需要剩餘容量計算，也不會出現超量確認視窗。

**Failure modes**

- 貼上內容全部無法解析（有效筆數為 0）：不寫入任何內容，回報區列出所有無效行，不顯示超量確認視窗。
- 超量確認視窗選擇「放棄」：不寫入任何一筆，且不建立任何批次。
- 批次已滿時按「＋」：以提示視窗說明並提供「開新批次」，這是有意讓使用者看見的說明，不是靜默失敗；選「取消」時不寫入任何內容。
- 以 deck 為目標時貼上的內容全部無法解析（有效筆數為 0）：不建立任何批次，回報區列出所有無效行。
- 批量寫入在不允許溢出且會超量時回傳 nil，呼叫端不得誤判為成功。

**Acceptance criteria**

`VocTestTests/CardEditorTests.swift` 新增覆蓋（`VocTestTests/GrammarItemEditorTests.swift` 對稱）：

- 剩餘容量：空批次等於 `capacity`；已滿批次為 0；持有 `capacity` 減 1 筆時為 1。
- 未超量：批次持有 32 筆、寫入 5 筆，批次變 37 筆，新寫入的 `importOrder` 為 32 至 36，每筆 `wrongCount` 為 0，deck 批次數不變。
- 超量且允許溢出：批次持有 32 筆、寫入 12 筆，目標批次填滿至 40，deck 新增 1 個批次持有 4 筆，總寫入 12 筆，新批次內 `importOrder` 由 0 起算。
- 超量且允許溢出、剩餘超過一批：批次持有 39 筆、寫入 83 筆，目標批次填滿至 40，其餘 82 筆切成 40、40、2 三個新批次。
- 超量但不允許溢出：回傳 nil，目標批次筆數不變，deck 批次數不變。
- 溢出建立的批次編號接續 deck 既有最大編號，且連續不重疊。
- 寫入新批次：以 deck 為目標寫入 1 筆，deck 新增 1 個含 1 筆的批次，其 `importOrder` 為 0，編號接續既有最大編號。
- 寫入新批次：以 deck 為目標寫入 83 筆，deck 新增 3 個批次，大小為 40、40、3。
- 寫入新批次：空輸入不建立任何批次，deck 批次數不變。
- 既有內容不受影響：目標批次原有項目的內容欄位、`wrongCount`、`importOrder` 在批量寫入後皆不變。

程式碼審閱條件（不開模擬器）：

- 兩個預習頁的「＋」無 `.disabled`，action 內先檢查 `canAppend`；false 分支先顯示提示視窗，且只有在使用者選「開新批次」後才開啟選單，「取消」分支不呼叫任何寫入函式。
- 兩個預習頁的「＋」true 分支開啟選單，選單恰有兩項，分別導向編輯畫面新增模式與批次貼上畫面。
- 兩個貼上畫面的寫入路徑呼叫對應 Editor 的批量寫入函式，而非自行建立模型物件或自行切批。
- 兩個貼上畫面在超量時顯示確認視窗，「放棄」分支不呼叫任何寫入函式。
- 溢出路徑與所有「寫入新批次」路徑最終都由 `CardImporter.appendCards` 或 `GrammarItemImporter.appendItems` 完成，專案中沒有第二處切批實作，也沒有任何地方建立不含內容的批次。

**Scope boundaries**

在範圍內：兩個 Editor 的剩餘容量、批量寫入與寫入新批次、兩個批次貼上畫面（支援批次與 deck 兩種目標）、兩個編輯畫面新增模式的 deck 目標、兩個預習頁的「＋」選單與滿載提示視窗、超量確認視窗、對應單元測試、三份專案說明文件的更新。

不在範圍內：deck 層級匯入頁、解析器、批次容量數值、測驗與錯題複習流程、編輯畫面的既有欄位與驗證、`content-deletion` 的多選刪除、既有批次的重新切分、從檔案匯入到單一批次。

## Risks / Trade-offs

- 「＋」多了一層選單，只想手動加一筆的使用者要多點一次 → 這是提供第二條路徑的必然成本。選單只有兩項且「手動輸入一筆」排在第一，多出的操作是一次點擊。
- 滿載時要先過提示視窗再過選單，共兩層 → 提示視窗承載「為什麼你接下來看到的是新批次」這個必要資訊；少了它，使用者在滿批次按新增卻得到新批次的內容，就回到 `add-content-editing` 兩度否決的「無法預期」問題。
- 溢出建立的新批次在 deck 末端，使用者當下看的仍是原批次，可能沒注意到新批次已產生 → 匯入結果回報區明確顯示新增筆數與新建批次數，與 deck 層級匯入頁的回報格式一致。
- 批量寫入與單筆新增是兩條寫入路徑，驗證規則可能分歧 → 兩者共用同一個 `isValid` 與同一個 `capacity` 來源；批量寫入內部也會過濾未通過驗證的項目。
- 驗收不含模擬器互動，選單與確認視窗的綁定錯誤不會被自動化擋下 → 以 Acceptance criteria 中的五項程式碼審閱條件涵蓋，且所有寫入與容量規則都在 Model 層有測試。
